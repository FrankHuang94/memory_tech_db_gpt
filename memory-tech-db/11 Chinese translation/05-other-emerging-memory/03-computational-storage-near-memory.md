# 计算存储与近内存计算

> [查看英文原文](../../05-other-emerging-memory/03-computational-storage-near-memory.md)

计算存储和近内存计算反复出现，因为现代系统越来越受“搬数据”而非执行简单计算限制。把压缩、过滤、扫描、加密、索引或部分 AI 算子移到 SSD、存储网络、CXL 内存或 HBM 堆栈附近，理论上可减少 PCIe、网络与主机 DRAM 往返，降低功耗并释放 CPU/GPU 周期。但距离数据更近并不自动等于更好：可编程性、数据一致性、安全、调试、运维和工作负载可重复性决定其是否能超出利基市场。

## 为什么该理念不断回归

存储容量增长快于 CPU 到存储的可用搬运能力。数据库扫描、日志分析、备份、ETL、向量检索和检查点常读取大量数据，却只保留少量结果。若先搬完整数据到 CPU 再过滤，I/O、内存带宽和能量被浪费；若设备近端先下推谓词、解压或选择候选，主机只接收有用字节。关键不是“在存储上运行任意程序”，而是对稳定、可隔离、数据移动占主导的算子进行下推。

## 计算存储：从 SmartSSD 到压缩 SSD

SmartSSD/计算存储通常在 SSD 控制器旁加入 FPGA、ARM 核或专用逻辑，可做压缩/解压、校验、加密、过滤、正则/检索预处理和有限数据库扫描。最成熟的商业形态往往不是通用计算，而是透明压缩、加密、去重、RAID/ECC、数据完整性和协议卸载：这些功能边界清晰、数据局部、可验证且不需要客户维护异构应用。

限制来自 NAND 与控制器的真实职责。SSD 控制器已要执行 FTL、GC、wear leveling、ECC、掉电保护和 QoS；增加用户计算会争夺 SRAM、DRAM、功耗与热预算，并可能损害尾延迟。设备端代码升级、故障隔离、可观测性和多租户安全也比 CPU 程序困难。因此采购时应确认：下推的算子、每秒有效输入/输出、对 P99 延迟的影响、写放大、热节流，以及 CPU 端软件是否仍是主要瓶颈。

## SSD 邻近数据研究、NVMe-oF 与 SmartNIC

研究系统常把 ANN、列存扫描、压缩、键值过滤或图算法放在 SSD 附近，展示可观的数据移动节省。研究结果应与量产价值分开：原型可能假设固定数据布局、没有多租户、忽略固件生命周期，或用不可复制的 FPGA 资源。真正有希望的场景是读多、算术密度低、结果缩小明显、可批处理且错误语义简单的任务。

NVMe-oF 和 SmartNIC/DPU 处于相关但不同的位置。它们把协议处理、RDMA/TCP、加密、虚拟化和安全策略从主机 CPU 卸载到网络边缘，主要节省网络/CPU 开销而非 NAND 媒体延迟。对于分布式存储，常先通过更好的网络卸载和数据布局获得收益，再考虑把应用算子塞进 SSD。安全卸载尤其有价值，但密钥、证明、更新和隔离必须由平台统一管理。

## CXL 近内存计算与 HBM-PIM

CXL 设备可将容量与简单处理组合，在内存附近做页面扫描、压缩、数据库过滤或 AI 数据准备。其潜在优势是避免把大量冷数据拉入 CPU cache/DRAM；风险是 CXL 一致性、设备编程和 fabric QoS 尚复杂，且通用 CPU 往往更容易调试和更新。CXL 近内存逻辑应优先处理清晰的批量算子，而不应成为隐藏、难以观测的“第二主机”。

HBM-PIM/内存堆栈计算更靠近高带宽热数据。逻辑 die 或内存附近单元可执行向量、归约、推荐嵌入或特定 AI 操作，减少在 HBM 与计算核之间搬运。它具有潜在带宽/能效优势，却面对编程模型、精度、调度、热、验证和生态问题。若数据必须每个周期在 GPU tensor core 上使用，PIM 未必有利；若任务是带宽受限、可并行、算术强度低的操作，才更有可能赢。

## 市场结构与采用障碍

价值链包括 NAND/DRAM/HBM、SSD/内存控制器、FPGA/ASIC、DPU/SmartNIC、交换机、系统软件、数据库和云服务。市场不一定奖励“最靠近介质”的芯片；往往是拥有数据格式、软件接口、客户工作负载和机队运维能力的一方捕获价值。供应商应证明节省的是端到端成本，而非把复杂度从主机转移到固件。

主要障碍包括碎片化 API、缺少可移植编程模型、调试与性能分析困难、固件更新风险、安全隔离、设备资源有限、标准化不足以及客户不愿为单一应用维护专门路径。数据一致性也很关键：下推操作与主机缓存、事务、故障恢复和重试必须有清楚语义。

## 工作负载匹配与买方尽调

良好匹配：压缩/解压、加密、校验、列过滤、搜索候选粗筛、日志扫描、ETL 和网络协议卸载；它们通常批量、可并行、输出小于输入。谨慎匹配：ANN 精排、图计算、数据库算子和推理前处理，需要数据布局与框架集成。较差匹配：细粒度高依赖逻辑、强事务一致性、频繁随机更新、严格低尾延迟或需要频繁更改算法的工作负载。

尽调应问：基线是什么、数据移动占总时间/能量多少、加速是否在真实并发和 P99 下成立、是否增加写放大或设备故障域、API 是否可移植、如何监控/更新/回滚、租户如何隔离、发生错误时主机能否安全接管。若没有端到端基准和运营计划，“近数据”通常只是演示。

## 展望

近期最可持续的机会仍是固定功能卸载和平台级 DPU/压缩/安全；中期是数据库、检索和 AI 框架把少量成熟算子显式下推；长期才可能出现更广泛的 CXL 近内存和 HBM-PIM 编程模型。成功条件不是芯片能做更多，而是以更低 TCO、可预测 QoS 和可维护安全性完成原本必须搬运的数据工作。
